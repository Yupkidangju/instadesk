# 감사 4 수정 계약 (2.1.1)

작성일: 2026-11-02. 원본 `docs/audit/audit_report_4.md`는 수정하지 않는다.

## 목표와 범위

`IMP-F007`~`IMP-F009`, `DBG-F011`~`DBG-F013`, `SEC-F005`~`SEC-F007`을 현재 Electron 앱에 대조한다. 자동 잠금, PTY 준비·진단·제한 재시도, 입력 비밀 수명, 볼트 v1→v2 이행을 순서대로 고친다. 사용자 최신 지시에 따라 동일 키 5대의 실 PTY·SSE 검증은 이번 자동 검증에서 제외하고 사용자 직접 수용 검사로 남긴다. VM 생성·삭제·상태 변경은 범위 밖이다.

## 동결한 계약

1. 비활성 15분은 **앱에서 사람이 입력한** 키·포인터·터치 활동 기준이다. 자동 조회와 네트워크 응답은 연장하지 않는다. 잠금 때 요청·PTY·Desktop·Broadcast와 화면의 비밀 입력을 정리한다. 잠금 직전 진행 중 요청이 끝나도 잠금을 취소하지 않는다.
2. WebSocket `open`은 연결 수립일 뿐이다. 서버의 유효한 `session` 텍스트 프레임 뒤에만 `PTY LIVE`로 표시한다. 소켓 수립 뒤 15초 안에 `session`이 없으면 준비 실패로 닫고 일시 네트워크 범주로 처리한다. `taken`, `error`, `exit`, 401/403/409/429/503 및 close code를 구별한다. 진단 데이터에는 타일 ID, 시간, 허용된 코드·범주만 남기며 URL·토큰·키·서버 임의 문자열은 IPC/로그에 전달하지 않는다.
3. 429는 유효한 `Retry-After`가 있으면 존중하고, 503·일시 네트워크 실패와 함께 최대 **3회 재연결**한다. 지수 지연은 기본 1·2·4초에 최대 20% 지터, 기본 지연 상한 30초다. `Retry-After`가 10분을 넘으면 자동 재시도하지 않는다. 인증 오류·`taken`·409·정상 종료는 자동 재시도하지 않는다. 잠금·타일 닫기·프로필 삭제·수동 재연결은 예약된 재시도를 취소한다. 각 시도는 새 PTY 티켓을 받는다.
4. 서비스의 8개 PTY 한도는 **user 단위**다. 앱은 user ID 및 다른 클라이언트의 열린 PTY를 알 수 없으므로 로컬 카운트를 서버 쿼터로 강제하지 않고 “이 앱에서 관측한 PTY / 서버 user 한도 8”로 표시한다. 서버 거절이 최종 판정이다. Desktop과 SSE `exec`를 PTY 수에 합산하지 않는다. Broadcast는 PTY 없이 독립된 SSE `exec`이며 대상별 성공·실패를 표시한다.
5. 신규 볼트 v2는 PBKDF2-HMAC-SHA256 600,000회, 신규 마스터 암호문구 최소 15자다. v1(100,000회·최소 6자)은 기존 암호로 읽고, **성공적으로 모든 프로필을 복호화·재암호화한 뒤 한 번의 저장소 쓰기로** v2로 이행한다. 실패·저장 실패에는 원본 v1을 유지하고 잠금을 유지한다. 약한 기존 암호는 자동 이행 후에도 강해지지 않으므로 UI에서 변경을 안내하고 암호문구 변경 경로를 제공한다. 기존 암호를 모른다면 복구·리셋하지 않는다. 재암호화는 서버 키 회전을 대신하지 않는다.
   폴링 중 `lastUsedAt` 갱신과 새 프로필 추가가 겹쳐도 최신 프로필 목록을 덮어쓰지 않아야 한다. 조회 메타데이터 갱신은 저장 직전 최신 레코드를 다시 읽고 병합하거나 생략한다.
6. 모달의 비밀번호·미제출 API 키는 닫기·취소·잠금·실패·성공 후 지운다. 입력값은 디스크와 로그에 쓰지 않는다. JS 문자열의 물리적 메모리 소거를 보장하지 않는다.
7. Windows/Linux의 Electron `userData`와 Chromium `sessionData`는 제품명 `InstaDesk`의 버전 없는 사용자 앱 데이터 경로로 고정한다. 볼트 저장소 키 `instabox_deck_vault_v1`은 v2 스키마에서도 유지해 기존 레코드를 찾는다. 패키지 폴더·버전·실행 위치를 바꿔도 같은 OS 사용자라면 프로필이 보여야 한다. 설치 폴더 삭제는 볼트 삭제가 아니다. 새 볼트를 생성하기 전 기존 저장소가 보이면 덮어쓰지 않는다.

## 구현·검증 순서

1. 이 계약과 `spec.md`/`designs.md`/결정 문서를 먼저 동기화한다.
2. 각 결함을 재현하는 회귀 테스트를 추가해 실패를 확인한 뒤 볼트·잠금·UI·PTY 게이트웨이/화면을 수정한다.
3. 타입 검사, 전체 테스트, 빌드, 의존성 감사 후 모의 5대 PTY 실패·회복, 5대 Broadcast 분리, 취소 경로, 키 프로필 5개 저장·재실행·v1→v2 이행을 검증한다. 실 5대 PTY·SSE의 HTTP·exit 결과는 사용자 직접 확인 전까지 미검증으로 기록한다. 비밀·명령 출력은 기록하지 않는다.
4. finding ID별 결과·미검증 범위를 새 재감사 문서에 남기고 2.1.1을 커밋·푸시·태그한다. 세 아키텍처 CI와 공개 릴리스 자산을 검증한다.

실 VM 5대 존재는 사용자 확인이지만, 이번 재감사에서 앱 연결 결과를 얻었다고 주장하지 않는다. 사용자의 후속 직접 수용 검사에 필요한 상태·오류 범주를 제공한다.
